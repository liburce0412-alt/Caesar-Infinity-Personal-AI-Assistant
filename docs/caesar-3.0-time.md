# Caesar 3.0 北京时间统一

状态：相关本地回归、构建及 lint 已通过。保留数据升级后的实机显示首页/个人页当前连续天数均为0，历史成就保留；课表周为10月12日至18日，确定性问时与设备秒级时间吻合。尚未发布。

## 约定与实现

- `CaesarTime.zone` 固定为 `Asia/Shanghai`。服务器带偏移的时间串先解析为 Instant，再格式化北京时间；树洞、留言、私聊不再截取 UTC 字符串。无效或不带偏移的远程时间显示“时间未知”，心愿显示“记录时间未知”。
- 时间记录展示、完成日、日/周/月统计、连续天数、贡献图、日目标新快照、健康日窗口、课程日期、提醒与超级岛使用同一默认时区。首页/个人页连续天数/时间页/贡献图/课表/心愿列表的日期在前台跨日或恢复前台时更新；检查不唤醒后台，只有日期变化才更新 Compose 状态。
- 个人页“连续天数”与首页统一取当前北京业务日的连续记录数，不再与远端 `profile.streakDays` 取最大值。已核对 `20260922070550_completed_time_statistics.sql`：远端字段通过 `greatest(streak_days,longest_streak)` 保留历史最长值，适用于成就，不代表当前连续天数；成就仍保留该历史值，数据库与远端不改动。复用现有 `TimeRecordCalendar` 边界和个人页 UI 测试，由主任务统一验证。
- 存储继续使用 epoch/Instant；没有给历史记录加 8 小时。旧 `localDate`、心愿目标日与学期日期仍按纯日期解释，不迁移、不改写旧日期键。
- Material DatePicker 的 selectedDateMillis 继续以 UTC 午夜编码纯日期；这不是用户的事件发生时刻。首次打开的月份以北京今日为准，往返仍保留原日期。
- Mi Fitness 新请求与缓存读取默认采用北京当天。旧设备时区形成的缓存若时间窗口不一致，拒绝将其当作北京今日，但保留原缓存；下次明确同步取得正确窗口的数据。账号隔离与健康授权保持原流程。
- ICS 的 `Z` 与显式 `TZID` 仍决定来源时区，导入目标默认北京时间；纯 UTC 存储、外部日历来源语义没有机械替换。

## 本地回归范围

新增/扩展 `CaesarTimeTest`、`WishTimeTest`、`MiFitnessStepsSyncServiceTest`、`MiFitnessSummaryHealthGatewayTest`、`CourseReminderNotificationTest`，覆盖：

- 同一瞬间 `Z` / `+08:00` 与带小数秒的服务端时间显示一致；未知/无偏移时间不会伪装“刚刚”。
- 北京 23:59:59 → 00:00:00，在洛杉矶、UTC、基里蒂马蒂设备时区下保持相同日期。
- 跨午夜记录的完成日、统计、连续天数、贡献日与健康窗口一致。
- 旧纯日期键和 DatePicker UTC 编码往返保持原日期、原 epoch 数据不变。
- 默认 Mi Fitness 日期忽略设备/Clock 的时区；不匹配的旧缓存被拒绝且保持原数据，新北京窗口可读取。
- 普通课程通知与超级岛在异区设备上显示相同北京时段，通知定时 epoch 不改变。

静态检查与相关单元回归通过，汇总结果见总验收记录。用户已恢复手机操作授权；当前日期和问时检查通过，但跨日 UI、系统提醒实际交付及真实健康同步尚未通过实机验收。

## 与主任务的衔接

AI 层 `AiContext`、`CampusAiTasks`、`AiViewModel` 和 `AiScreen` 由主任务接入 `CaesarTime`。数据库旧迁移中的新执行日目标回填应使用固定北京日期（`strftime` 的 `+8 hours`），已有键不重写；数据库修改由主任务负责。
