## 需要优先修复的缺陷

### A1 · P1 · 课程去重与回填缺少账号边界

- 位置：`AppDatabase.kt:156` 的 `sourceHash` 全局唯一索引、`:395` 的无账号查询；`CampusSyncWorker.kt:177` 的 fallback 查找与 `:183` 的整行回填。
- 触发：同一设备先使用 A 账号，再用 B 账号导入/同步相同课程。课程哈希未包含账号。
- 结果：B 的本地插入被 `IGNORE` 跳过；拉取 B 的同哈希课程会命中 A 的行，在该行已同步时把它覆盖为 B 的数据，A 的本地课程随之消失。远端 RLS 不能防止本地串写。
- 证据：用仓库导出的 Room v8 建表语句与索引、实际 DAO 查询，在内存 SQLite 中复现：`second_account_inserted=0`、`fallback_lookup_matched_owner=alice`、`first_account_rows_after_pull_update=0`。
- 建议：迁移到 `(userId, sourceHash)` 唯一约束，所有 fallback 查询附带 owner；明确本地访客课程归属转移规则。补 A/B 同哈希、访客认领、软删除后重新导入的 Room 测试。

### A2 · P1 · 同步回包能覆盖请求期间的新编辑

- 位置：`CampusSyncWorker.kt:46–85`、`:93–134`；`AppDatabase.kt:319`、`:398` 的 `@Update`。
- 触发：Worker 读取行并等待网络，用户在此期间编辑或删除同一条记录。
- 结果：成功、失败两条分支都写入 `local.copy(...)` 的旧完整快照，没有以本地版本/更新时间做条件更新；新编辑会被旧正文覆盖，甚至被标成已同步。仅在 RPC 端检查版本无法解决客户端回包时的竞争。
- 证据：使用真实 DAO 的编辑 SQL 和 Room 全实体更新语义模拟确定性的交错顺序，新标题被恢复为 `Original`，状态变成 `synced`。
- 建议：回包仅更新同步元信息，并用 `WHERE id=? AND version=? AND updatedAt=?` 做 compare-and-set；不匹配时保留 pending。网络异常分支也不能回写旧正文。成功回包、失败回包、删除/撤销均需覆盖。

### A3 · P1 · 超过 200 条的聊天读不到新消息，却可能清掉未读

- 位置：`CampusRepository.kt:396–407`，查询 `created_at.asc + limit=200`；`CampusViewModel.kt:278–288`；`20260822054106_messaging_order_workflows.sql:100–110`。
- 触发：会话已有 201 条及以上消息，重新打开会话。
- 结果：始终显示最早 200 条，没有 offset/cursor 或加载更多。随后无论读取成功与否都调用 `markConversationRead`，SQL 把 `last_read_at` 设为现在；未展示的新消息也可能被标为已读。本机刚发送的消息能暂时追加，重进后仍会被截掉。
- 证据：客户端查询/调用顺序和数据库函数相互印证；未在生产会话注入测试消息。
- 建议：先取最新一页再按时间正序显示，向前游标分页；只在成功显示后将已读水位推进到实际展示的最后消息时间/ID。增加 201 条消息及读取失败用例。帖子评论、心愿评论的 `asc + limit=200` 也需要分页策略。

### A4 · P2 · 离线同步永远只拉最早 1000 条

- 位置：`CampusSyncWorker.kt:140–172`。
- 时间记录、课程查询均为 `updated_at.asc + limit=1000`，没有分页循环、游标、offset 或增量水位。
- 一旦包含删除标记在内的数据超过 1000 行，新设备永远缺少后续数据；较新的更新也可能落到首批范围外。Worker 仍可返回成功。
- 建议：按 `(updated_at, id)` 稳定游标遍历，成功应用一页后再持久化水位；为 1001 条、同时间戳、删除标记和中途失败增加测试。

### A5 · P2 · 冲突记录进入无法自动恢复的状态

- 位置：`CampusSyncWorker.kt:78,127,158,182`；`AppDatabase.kt:313,389`。
- RPC 返回冲突后只保存远端版本/更新时间，正文保留本地并标记 `conflict`；push 只查 `pending/failed`，pull 只更新 `synced`。全项目没有处理这个同步状态的解决入口。
- 结果：多设备编辑冲突后，本地与远端长期不一致，界面也不提醒用户。课程没有编辑入口，尤其难以恢复。
- 证据：内存 SQLite 复现 `conflict` 记录不进入待重试集合；全局检索确认未实现冲突解决分支。
- 建议：保留本地/远端两份冲突信息，提供明确的采用远端/重新提交决策，或制定产品接受的合并策略。不要直接把标志改成 `synced` 掩盖不一致。

### A6 · P2 · ICS 导入丢失时区与实际授课日期

- 位置：`ScheduleImporter.kt:74–84,115–119`。
- `20260922T000000Z` 经 `toLocalDateTime()` 后变成 00:00，未转换为设备时区；对中国用户，本应为 08:00。带 `TZID` 的属性参数也被 `property()` 丢弃。
- 所有包含 WEEKLY 的 RRULE 都简化为“每周”；`INTERVAL=2`、UNTIL、COUNT、EXDATE、BYDAY 未正确保留，单次事件也只剩星期。日期型全天事件还可能让一次导入整体失败。
- 建议：引入成熟 iCalendar 解析器前先确认许可证/Android 兼容性，建立保留起始日期、时区、重复规则与例外日期的中间模型；无法表达时在预览明确提示，而不是猜成每周。用 UTC、TZID、隔周、排除日期和跨午夜样本验证。
- 本次课程表视图明确标注“全部安排，查看周次”，但未改造原解析器，因此这一缺陷仍存在。

### A7 · P2 · 截图导入会把几何位置猜成固定上课时间

- 位置：`ScheduleImporter.kt:92–111`。
- 星期匹配前缀可选，课程名中的“一”“日”等字也可能被当作表头；图片纵向位置被强行分成五段并映射到固定的 08:00/10:00/14:00/16:00/19:00，没有读取真实节次时间。
- 结果：不同学校节次、午休长度或裁剪图片，会生成看起来有效但实际错误的课程时间。
- 建议：严格识别表头与时间轴，把 OCR 文本、格子归属、时间解析拆成独立阶段；无可靠时间轴时保留“待确认”状态。本次已修复表单校验，但尚未重做 OCR 算法。

### A8 · P2 · 同一条跨午夜记录在不同页面归属不同日期

- 位置：`DomainModels.kt:40–60`、`HomeTimeScreens.kt:165,1050–1052,1525`、`ProfileScreen.kt:882–884`、`TimeViewModel.kt:154–170`。
- 贡献图明确使用完成日 `endTime`；首页/时间轴/连续天数的部分路径仍使用 `startTime`。例如 23:50 开始、00:20 结束的记录在贡献图和“今日”统计中归到不同天。“周/月”还有滚动 7/31 天与自然周/月两种口径。
- 建议：将日界线、跨日分配、自然周/月、连续天数集中成一套业务计算，UI/AI/SQL 聚合复用明确口径。重构前先补跨午夜、月底、DST 与零时长样例。

## 条件性风险与维护建议

### R1 · 大文件按职责拆分，先保留已有行为

当前物理行数：`AiScreen.kt` 2495、`ProfileScreen.kt` 2090、`HomeTimeScreens.kt` 1531、`AiViewModel.kt` 1455、`OpenAiCompatibleClient.kt` 1211。

- AI ViewModel 同时管生成、图片、记忆、健康账号/同步、每日问候和历史。可先抽出健康协调器及图片导入控制器，再收敛会话状态机；保留已有 epoch、取消和写入协调保护，不做整体重写。
- Profile 页面把小米健康、自动任务、本地模型与展示组件放在同文件；按现有设置分区拆文件即可，不需要新导航架构。
- Home/Time 已有独立课程表组件，本次仅完成这一处拆分；其余专注、时间记录编辑和首页统计可分步整理。
- `AiContext.kt:250` 与 `CampusAiTasks.kt:218` 各维护一次课程冲突计算；都忽略周次，却输出 `computedConflicts`。建议合并为课程领域计算，区分时间重叠与实际教学周冲突。

### R2 · 长时间轴未真正使用惰性列表

`HomeTimeScreens.kt:1153–1167` 在一个 LazyColumn item 内用 Column + `filtered.forEachIndexed` 创建所有记录。外层 LazyColumn 无法逐条回收这些行。应改为带稳定 ID 的 `items(filtered)`，统计与分组使用 remember/上游计算；大数据量时考虑 Room Paging。尚未做真机帧率测量，不能把潜在开销写成已测出的卡顿幅度。

### R3 · 管理台拆包、类型与查询节流

- 实测生产主 JS 为 655.53 kB，gzip 194.75 kB；Vite 报单包超过 500 kB。`router.tsx:3–6` 静态引入全部页面，可按路由懒加载；别仅调高警告阈值。
- `backend.ts:6,14` 用 `Promise<any>` 丢失 RPC 契约；`DataPage.tsx` 同时做路由配置、查询、表格、弹窗、字段映射和写操作。先建立 RPC 输入/输出类型和按业务分类的操作函数，再拆展示组件。
- `InvitationsPage.tsx:12`、`DataPage.tsx:41` 将每次输入直接用作远端查询 key；可加短 debounce，并将 query signal 传入请求，避免快速打字产生多次无需完成的请求。
- 现有管理台单元测试仅 1 文件 / 2 用例，主要测总览。角色变化、草稿并发、邀请码失败、分页、缓存隔离更值得补测，而不是增加静态快照数量。

### R4 · 旧部署入口与当前部署说明不一致

`.github/workflows/deploy-supabase.yml:31,40` 仍硬编码托管 Supabase 项目；`deploy/alicloud/README.md` 描述香港自托管，并明确不应用旧托管工作流处理自托管迁移。当前工作流虽有手工确认，但目标没有让操作者明确核对。

建议将入口标为历史用途或拆分明确的目标环境、保护规则与迁移流程。这里只确认源码与文档不一致，未读取当前密钥或验证线上实际部署，也未关闭现有工作流。

### R5 · 遗留 AI Edge Function 的输入边界

`supabase/functions/ai-chat/index.ts:50` 对每条 message 直接读取 `.role`；`messages:[null]` 会抛 TypeError，逃出 JSON 解析的 try/catch。已用 Node 执行源码中同一校验表达式复现。应先检查每项非 null 对象，并为畸形输入返回 400。

当前 Android 生成路径使用个人云端/本地引擎；自托管瘦身脚本也未保留 Edge Runtime。因此不把此问题宣称为当前线上 Android 路径已发生的故障。若重新启用旧网关，还需核对共享额度计数、上游 EOF/SSE 完整性和取消传播。
