## History reads

`observeAiReportSummaries(ownerUserId, limit)` returns only metadata and an explicitly bounded window. The UI can request one extra row to detect more history and increase its window on demand. `getAiReportSummaryPage(ownerUserId, beforeUpdatedAt, beforeId, limit)` offers keyset pagination for older pages; pass both cursor values from the last row together. Both use `updatedAt DESC, id DESC`, so equal timestamps have a stable order. Neither query selects `messagesJson`.

The UI uses `AiReportSummary`, which cannot accidentally be saved as a complete conversation. Opening or deleting a row loads `getAiReport(id, ownerUserId)` first. Undo retains that complete report, its original timestamps and its original owner; it never reconstructs messages from a summary. All database writes reject changing the owner of an existing conversation ID.

## Ownership and compatibility

Database migration 10 → 11 adds `ownerUserId` and an index for history reads. Version 10 did not store reliable account ownership. Existing conversations therefore remain under `local_user`, accessible through the explicit local-history scope; migration does not guess an account, rewrite conversation content, move image files or alter timestamps. Newly saved account conversations receive the captured account owner. Account switches must cancel work and reset history subscriptions before another account's state is presented.

The existing foreground health automation is a device-local task with device-local consent. Its conversation writer explicitly keeps `local_user`. This change does not invent account ownership for those tasks or expand health disclosure consent.

Continuing a legacy conversation while logged in creates a new conversation ID under the current account before sending. The original report and its owner remain unchanged. Available history images and unsent attachments are copied into the new conversation's private directory; copy failures stop continuation with an error, while already-missing images retain their missing-image notice. Deleting either conversation cannot remove the other's image files.

Opening legacy image history also preserves retryability: if a source file still exists but migration cannot copy it, the entire report rewrite is stopped and the original JSON/source remain intact. Reopening retries migration after the storage issue is resolved. Existing missing-image counts survive migration of other messages. A real ViewModel regression blocks the target attachment directory, checks the failure leaves the report byte-for-byte unchanged, then removes the blocker and checks reopening succeeds without deleting the source.

History replay is cleared synchronously when its scope changes, and Room emissions carry the selected owner and query revision. Opening, sending, confirmation, new-conversation and account changes invalidate earlier loads. Account changes cancel Agent confirmation state and greeting work; greeting completions check the captured owner and Beijing date. Saving captures the regeneration tail and revision before waiting for the shared report write lock, and older completions cannot replace newer UI messages.

Delete returns success only after the full report has been captured and its owner-scoped database delete has completed. The snackbar's undo targets that exact report ID. Undo retains the original owner; image cleanup checks under the same write lock that the report was not restored. Delete/restore failures are reported rather than presenting an early success.

The same v11 migration now preserves legacy free-text memories under `local_user`. Memory management has a separate, explicitly labelled “本机旧记忆” scope; its list is synchronously cleared on account/scope changes, and edit/confirm/delete operations capture that scope's owner. Switching account also closes stale memory edit/delete dialogs. Automatic confirmed-memory context is loaded only for requests already constrained to local execution and only for the captured request owner. Any turn that reads free-text memory is marked sensitive so it cannot later be replayed to a cloud route. Legacy memories are never automatically attached to a logged-in account's request.

Existing date keys are untouched. The older 6 → 7 migration now uses UTC plus eight hours only when initially deriving Beijing date keys for installations still below version 7; it does not reapply any shift to stored keys or epoch timestamps.

## Diagnostic retention

`insertAgentTrace` inserts and prunes in one Room transaction. Across the entire local database, only the latest 200 diagnostic events survive, ordered by `createdAt DESC, id DESC`. A single global cap prevents storage growing with the number of accounts. Reading or explicitly clearing diagnostics remains owner-scoped. A trace stores the owner captured in its originating request, not whichever account is active when a delayed event completes.

The 10 → 11 migration also trims pre-existing diagnostic overflow. Retention touches only `agent_traces`: AI conversations, personal memories, time records, community records and persistent action/idempotency state are outside its deletion scope. A failed prune rolls back the insertion.
